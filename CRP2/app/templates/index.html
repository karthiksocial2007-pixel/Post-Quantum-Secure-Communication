Complete protection flow

ML-KEM-768 establishes the shared secret. HKDF-SHA256 derives the AES session key. AES-256-GCM encrypts the message. ML-DSA-65 signs the message. The receiver decrypts the message and verifies the signature before accepting it.

SECURITY TESTING

Security Attack Simulation

Demonstrate how the system responds to common attacks against secure communication.

⚠️
ATTACK 01

Ciphertext Tampering

An attacker modifies encrypted data before it reaches the receiver.

Expected: Bob rejects the message on Receive (AES-GCM tag fails).
✍️
ATTACK 02

Message Modification

An attacker changes the message after it has been digitally signed.

Expected: Bob rejects the message on Receive (ML-DSA signature fails).
🔁
ATTACK 03

Replay Attack

An attacker attempts to resend a previously processed message.

Needs: a message that was already received. Resends are blocked.
🔑
ATTACK 04

Wrong Session Key

An attacker attempts to decrypt the packet using another session key.

Passive: packet is not changed, so Receive still succeeds.
👁️
ATTACK 05

Packet Interception

An attacker captures the packet while it travels through the communication relay.

Passive: packet is only copied, so Receive still succeeds.

HONEST SCOPE

Project Limitations

This is an academic demonstration, not a production messenger.

  • The relay and all session state live in server memory (no database).
  • There is no login system, and public-key distribution (PKI) is simplified.
  • The ML-KEM handshake itself is not authenticated in this demo.
  • Packet interception is not detected; it is made useless by encryption.
